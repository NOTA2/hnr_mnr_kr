# GBA 한글화 진행 순서

이 문서는 "GBA 게임 한글화를 전혀 모르는 상태"를 기준으로, 실제 작업이 어떤 순서로 진행되는지 쉽게 정리한 문서입니다.

## 한 줄 요약

지금 프로젝트 기준 권장 순서는 아래와 같습니다.

1. 한글 폰트 후보 확정
2. 폰트 매핑/표시 QA 확정
3. 남은 텍스트 추출 감사 마감
4. 번역 시작용 workset/메타데이터 정리
5. 번역/용어집 작성
6. 번역 감수
7. 자동 삽입 + 수동 미세조정
8. 이미지 추출/수정/재삽입
9. 실제 플레이 QA
10. 패치 제작/배포

중요한 점은 `번역`보다 먼저 `추출이 되는지`, `다시 넣을 수 있는지`, `한글이 표시되는지`를 확인해야 한다는 것입니다.
또한 실제 화면 QA 는 하나가 아니라,

- 폰트/삽입 경로를 보는 **기술 QA**
- 번역문이 자연스럽고 페이지가 맞는지 보는 **콘텐츠 QA**

둘로 나뉜다고 보는 편이 정확합니다.

## 왜 이런 순서가 필요한가

겉으로 보면 "일본어 문장을 한국어로 바꾸면 끝"처럼 보이지만, 실제 ROM 안에서는 아래 요소가 따로 존재하는 경우가 많습니다.

- 텍스트 데이터
- 텍스트를 가리키는 포인터
- 폰트 이미지
- 문자 코드 테이블
- 줄바꿈/색상/이름표시 같은 제어 코드
- 압축된 이미지와 UI 리소스

그래서 먼저 구조를 파악하지 않으면, 번역문을 써도 게임에 넣을 수 없거나 글자가 깨지는 일이 생깁니다.

## 실제 작업 순서

### 0. 폰트 테스트 단계와 본작업 단계를 분리하기

지금처럼 초반에는 테스트용 workbench, 비교 ROM, 비교 시트가 많이 생깁니다.

이 단계의 목적은:

- 어떤 한글 폰트를 seed 로 쓸지 정하기
- 자동 렌더링 후 사람이 손볼 때 가장 덜 힘든지 보기
- 실제 게임 시작 화면에서 가독성을 확인하기

즉 "완성 글꼴 제작"이 아니라 **정식 글꼴 제작의 출발점을 고르는 단계** 입니다.

### 1. 한글 폰트 후보 확정

이제는 구조 조사보다, 어떤 폰트를 정식 seed 로 삼을지 먼저 정하는 편이 맞습니다.

여기서 결정할 것:

- 기본 seed 폰트
- 폰트 라이선스
- startup intro / core UI 기준 가독성
- 자동 렌더링 후 수동 수정 난이도
- 한글과 숫자/영문이 같이 섞였을 때 모양

이 프로젝트에서는 현재:

- active 실험축: `D2Coding size11 cutoff 20%`
- 비교 가능 후보: `SourceHanSansKR`, `SourceHanMonoKR`
- 다음 우선 후보: `LanaPixel`, `Silver`, `Neo둥근모`, `PF스타더스트`, `굴림체`

### 2. 폰트 매핑과 표시 QA 확정

폰트 후보를 정한 뒤에는 실제 작업 전 아래를 먼저 끝내야 합니다.

- startup intro `14`글자 수동 보정
- core UI 우선 `48`글자 수동 보정
- 코드 매핑 범위 확정
- 폭/줄 수용량 문제 확인

이 단계가 끝나야 이후 번역문을 넣어도 화면이 계속 깨지지 않습니다.

### 3. 데이터 구조 조사

가장 먼저 해야 할 일은 "이 게임이 텍스트와 이미지를 어떻게 저장하고 있는가"를 파악하는 것입니다.

여기서 확인하는 것:

- 문자열이 평문으로 저장되어 있는지
- Shift-JIS/CP932 같은 일반 인코딩인지
- 전용 문자 테이블을 쓰는지
- 문자열 끝을 `00`, `FF` 같은 값으로 구분하는지
- 포인터가 어떤 형식으로 저장되는지
- 폰트가 타일 이미지 형태인지
- 이미지가 압축되어 있는지

이 프로젝트에서는 이미 일부 문자열이 `cp932 + 00 종료` 형태로 저장된 것이 확인되었습니다.

### 4. 텍스트 추출

다음은 ROM 안의 문자열을 파일로 꺼내는 단계입니다.

보통은 JSON이나 CSV로 추출합니다.

예:

- 원문
- ROM 오프셋
- 문자열 길이
- 종료 바이트
- 나중에 채울 `translation` 필드

이 프로젝트에서는 이미 일부 구간이 JSON으로 추출되어 있습니다.

- [item_texts.json](/Users/user/test/confirmed_data/extracted_texts/item_texts.json)
- [system_messages.json](/Users/user/test/confirmed_data/extracted_texts/system_messages.json)

### 5. 텍스트 재삽입 확인

이 단계는 매우 중요합니다.

추출만 되는 것과, 수정한 문자열을 다시 게임에 넣을 수 있는 것은 다릅니다.

여기서 확인하는 것:

- 같은 길이 문자열은 제자리 덮어쓰기 가능한지
- 더 긴 문자열은 다른 공간으로 옮기고 포인터 수정이 필요한지
- 포인터를 자동으로 찾을 수 있는지
- 제어 코드가 섞여도 안전하게 삽입 가능한지

현재 프로젝트의 툴은 이 단계까지 기본 골격이 들어 있습니다.

### 6. 번역 준비

번역 전에는 아래 두 가지를 같이 정리하는 편이 좋습니다.

- 고유명사/기술명/아이템명 용어집
- 화면 길이 제한이 심한 UI 번역 기준

즉 번역과 감수는 본문만 보는 것이 아니라, **용어 통일 + UI 길이 제약**을 함께 봐야 합니다.

### 7. 폰트와 문자 매핑 준비

한글화에서 많이 헷갈리는 부분입니다.

#### 폰트

화면에 보이는 글자 그림입니다.

예를 들어 `가`, `나`, `다` 모양을 실제로 ROM 안에 넣는 작업입니다.

#### 문자 매핑

ROM 안의 바이트를 어떤 글자로 해석할지 정하는 규칙입니다.

예를 들어:

- `01 = あ`
- `02 = い`
- `80 = 가`

한글화를 하려면 보통 둘 다 필요합니다.

- 한글 글자 그림
- 한글 문자 코드 매핑

즉, "폰트만 넣는다"로 끝나지 않고, "그 폰트를 어떤 바이트가 가리키는지"까지 맞춰야 합니다.

### 8. 번역문 작성

이제 실제 번역문을 작성합니다.

이 시점부터는 아래처럼 작업하면 됩니다.

- 추출된 JSON을 열기
- 원문 옆 `translation` 필드 채우기
- source family 와 `translation_expansion_opportunities` 를 확인하고, 확장 가능한 항목은 자연스럽게 쓰되 고정 슬롯만 byte 한계에 맞춰 줄이기

주의할 점:

- 일본어보다 한국어가 길어지는 경우가 많음
- 줄 수 제한이 있는 UI가 많지만, 일부 대사 bank 는 ROM 확장/재패킹으로 원문 byte 길이를 넘길 수 있음
- 메뉴/아이템명/전투 메시지는 길이 제한이 더 심함

### 9. 번역문 감수

감수는 별도 단계로 두는 것이 좋습니다.

주로 보는 것:

- 고유명사 통일
- 말투/톤 통일
- UI 길이
- 제어 코드 유지 여부
- 문맥상 오역

### 10. 번역문 삽입

작성한 한국어 문장을 실제 ROM에 넣는 단계입니다.

보통 두 가지 방식이 있습니다.

- 짧은 문장: 원래 위치에 그대로 덮어쓰기
- 긴 문장: 빈 공간에 새로 쓰고 포인터를 새 위치로 수정

이 프로젝트의 `apply-translations` 명령은 이런 흐름을 염두에 두고 만들어졌습니다.

### 11. 이미지 추출/교체

사용자님이 생각한 "이미지 추출 후 교체"도 맞는 방향입니다.

다만 텍스트와는 별도의 축으로 보는 것이 좋습니다.

보통 순서는 아래와 같습니다.

1. 이미지 리소스 위치 찾기
2. 압축 여부 확인
3. 추출
4. 편집
5. 원래 포맷으로 재삽입

주로 대상이 되는 것:

- 타이틀 로고
- 메뉴 버튼
- 튜토리얼 그림
- 상태창 텍스트가 박힌 UI 이미지

### 12. 실제 테스트

한글이 보인다고 끝이 아닙니다.

반드시 확인해야 하는 것:

- 글자가 깨지지 않는지
- 줄바꿈이 자연스러운지
- 화면 밖으로 넘치지 않는지
- 저장/전투/이벤트에서 문제 없는지
- 특정 문장이 게임 크래시를 일으키지 않는지

### 13. 패치 제작/배포

최종 단계에서는 ROM 자체가 아니라 보통 패치 파일을 배포합니다.

여기서 필요한 것:

- 패치 포맷 선택 (`bps` 권장)
- 사용법 문서
- 버전 정보
- 테스트된 ROM 해시 안내

## GUI 프로그램에 대한 현실적인 진행 순서

사용자님이 생각한 아래 방향은 최종 목표로 매우 좋습니다.

- GUI 프로그램에서 일본어 문장을 보고 한국어를 1:1 입력
- 이미지 추출 후 파일 교체

다만 실제 개발 순서는 보통 아래가 더 안전합니다.

1. 내부 엔진부터 만들기
2. JSON/CLI로 추출과 삽입 검증
3. 폰트와 포인터 처리 안정화
4. 그 위에 GUI 얹기
5. 마지막에 이미지 편집 기능 붙이기

이유는 GUI를 먼저 만들어도, 내부에서 문자열 재삽입과 포인터 수정이 안 되면 실제 패치가 불가능하기 때문입니다.

## 이 프로젝트에서의 권장 우선순위

현재 상태를 기준으로 다음 순서를 권장합니다.

1. startup intro 기준으로 정식 seed 폰트 확정
2. glyph editor 로 startup intro `14`글자 수동 보정
3. core UI 우선 `48`글자 세트 확정
4. 남은 텍스트 source 만 coverage 관점으로 마감
5. 번역/용어집/감수 루프 진입
6. 자동 삽입 + 수동 수정 루프 완성
7. 이미지 추출/교체 기능 확장
8. 최종 패치 제작

## 지금 바로 이해하면 좋은 핵심 개념

- `텍스트 추출`은 시작일 뿐이고, `재삽입`이 훨씬 중요합니다.
- `폰트`와 `문자 매핑`은 서로 다른 문제입니다.
- `이미지 교체`는 텍스트 작업과 병행 가능하지만 별도 축입니다.
- 초반에는 GUI보다 `분석 도구 + JSON + 자동 삽입기`가 우선입니다.
