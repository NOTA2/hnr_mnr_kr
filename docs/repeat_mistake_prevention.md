# Repeat Mistake Prevention

이 문서는 같은 실수와 같은 삽질을 반복하지 않기 위한 운영 규칙입니다.

새 세션이나 새 에이전트는 작업 전에 이 문서를 꼭 확인합니다.

## 목적

- 이미 틀린 가정을 다시 반복하지 않는다.
- 이미 확인된 사실을 다시 처음부터 의심하지 않는다.
- 이미 실패한 탐색을 같은 조건으로 재실행하지 않는다.
- 새 조사 결과를 "사실", "가설", "실패", "보류"로 구분해 남긴다.

## 가장 중요한 규칙

1. 추측과 확인된 사실을 같은 급으로 다루지 않는다.
2. 실패한 시도는 반드시 기록한다.
3. "왜 실패했는지"를 남기지 않은 실험은 끝난 실험으로 취급하지 않는다.
4. 다음 작업 전에 `이미 확인된 것`, `이미 실패한 것`, `아직 미확인인 것`을 구분한다.
5. 같은 실험을 다시 할 때는 반드시 조건이 무엇이 달라졌는지 적는다.

## 작업 전 체크리스트

작업 시작 전에 아래를 확인합니다.

1. [project_control_tower.md](/Users/user/test/docs/project_control_tower.md) 확인
2. 관련 트랙 문서 확인
3. [experiment_log.md](/Users/user/test/analysis/experiment_log.md) 확인
4. 이번 작업에서 다시 하면 안 되는 가정이 무엇인지 확인

## 작업 후 체크리스트

작업이 끝나면 아래를 갱신합니다.

1. 총괄 현황판
2. 관련 트랙 문서
3. 실험 로그
4. 필요하면 초기 조사 메모

## 자주 반복되기 쉬운 실수

### 1. 모든 텍스트 뱅크가 같은 구조라고 가정

이 프로젝트에서는 이미 틀린 가정입니다.

- 지역명 뱅크는 절대 포인터가 잡힘
- `0x3Dxxxx` 대형 뱅크는 같은 방식이 바로 안 잡힘

따라서 텍스트 뱅크별로 처리 전략이 다를 수 있습니다.

### 2. 일본어처럼 보이는 문자열 후보를 바로 진짜 텍스트로 확정

초기 단순 스캔은 코드/쓰레기 데이터도 많이 섞일 수 있습니다.

따라서 아래를 같이 봐야 합니다.

- 일본어 비율
- 제어 코드 패턴
- 주변 문자열 밀집도
- 실제 포인터 또는 사용 흔적

### 3. 문자열 한 군데를 바꾸면 게임 전체가 다 바뀐다고 가정

이미 일부 기술명은 여러 텍스트 뱅크에 중복 저장될 가능성이 보입니다.

따라서:

- UI용 문자열
- 전투용 문자열
- 설명용 문자열

이 서로 다른 저장소일 수 있습니다.

### 4. 실패한 탐색을 같은 조건으로 다시 반복

예:

- 절대 포인터 검색이 안 나왔는데 같은 조건으로 계속 재검색
- 필터 없는 문자열 스캔을 반복

이 경우에는 "탐색 조건을 바꿔야 한다"는 쪽으로 사고를 전환합니다.

### 5. 리소스 테이블 엔트리를 겹치지 않는 청크 경계로 단정

이 프로젝트에서는 이미 위험한 가정으로 확인되었습니다.

- `0x17C1C0` 부근 테이블은 `u32 length + u32 rom_address` 형식으로 보인다.
- 하지만 여러 엔트리가 서로 겹친다.

따라서:

- "엔트리 하나 = 독립 청크 하나"라고 바로 결론 내리지 않는다.
- 범위 기반 추출 JSON과 실제 디스크립터 경계를 구분해서 기록한다.
- 다음 조사 전에는 [resource_chunk_directory.md](/Users/user/test/analysis/resource_chunk_directory.md) 와 [resource_chunks.json](/Users/user/test/analysis/resource_chunks.json) 을 먼저 확인한다.

## 기록 규칙

### 사실

실제로 확인된 것만 적습니다.

예:

- `0x18425C` 지역명 뱅크는 절대 포인터가 확인되었다.

### 가설

아직 증명 전인 해석을 적습니다.

예:

- `0x3Dxxxx` 뱅크는 인덱스 기반 구조일 수 있다.

### 실패

실패한 시도와 이유를 적습니다.

예:

- `0x3D329C` 에 대한 일반 절대 포인터 검색은 유효한 결과가 없었다.
